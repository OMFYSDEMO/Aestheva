# Aestheva

Aestheva is an aesthetic and wellness marketplace: clients find verified clinics, salons, wellness centres and independent practitioners, then book and pay a deposit online. Phase 1 is Thiruvananthapuram.

**Owner:** Haswel Care Private Limited. Aestheva is Haswel Care's marketplace project. Hasta Wellness Clinic is Haswel Care's separate clinic project.

## What is in this repository

| Path | What it is |
|------|------------|
| `src/` | **The Aestheva app**: one Cloudflare Worker (Hono, TypeScript) serving the public website, the booking API and the Razorpay webhook. |
| `migrations/` | D1 database schema. |
| `public/` | Stylesheet and browser scripts served as static assets. |
| `seed/dev-sample.sql` | The prototype's fictional providers, generated by `scripts/build-dev-seed.mjs`. Local development and tests only. |
| `test/` | Vitest suite run inside the Workers runtime against an isolated D1. |
| `prototype/` | The clickable product prototype: consumer site, practitioner workspace and platform admin. State is kept in the browser. All providers, people and figures are fictional. |
| `dashboard/` | The marketplace dashboard for the operations team, built from sample bookings. |

## The app

### What works today

- **Website:** home, search with text, area, category and service-type filters, provider profiles with services, team, verification and reviews, and the policy and contact pages. Pages are rendered on the server, so search engines can index venues.
- **Live availability:** each practitioner's weekly rota minus existing bookings, on a 30-minute grid, at least an hour ahead and up to 60 days out.
- **Booking:** service, practitioner (or anyone available), date and time, client details, deposit. The booking and its time slots are written together; the database's primary key on slots makes a double booking impossible.
- **Deposits through Razorpay:** an Order is created for the deposit and paid in Razorpay Checkout. The booking is confirmed from the signed checkout callback, or from the webhook if the client closes the browser. Authorised-only payments are captured.
- **Holds:** an unpaid booking holds its time for 15 minutes; a cron job every 5 minutes releases expired holds. A payment that arrives late re-takes the time if it's still free, and is refunded automatically if not.
- **Managing a booking:** the client gets a private link. From it they can cancel: 24 hours or more before, the deposit is refunded in full through Razorpay; later, the deposit is kept unless they ask for a review, which opens a ticket for operations. A refund that fails is escalated as a ticket.
- **Every change is audited** in `audit_log`.

### Not built yet

- Practitioner workspace: calendar, marking appointments completed or no-show, time off.
- Operations console: provider applications and verification, refund reviews, tickets.
- Provider payouts with Razorpay Route: linked accounts, held transfers released on completion, weekly settlement. The schema already has a `razorpay_account_id` per provider and a commission rate on every booking.
- Booking confirmations and reminders by SMS, WhatsApp or email.
- Online provider applications (the page asks for an email until then).

### Run it locally

```sh
npm install --legacy-peer-deps
npm run db:migrate:local
npm run db:seed:local       # the prototype's fictional providers
npm run dev                 # http://localhost:8787
```

Without Razorpay keys, the deposit step offers a simulated payment, so the whole flow works offline. To try real Razorpay test mode locally, create `.dev.vars` with `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET`, and set `RAZORPAY_KEY_ID` in `wrangler.jsonc` to your `rzp_test_` key.

```sh
npm test                    # domain rules, booking and payment flows, pages
npm run typecheck
```

### Deploy to Cloudflare

The site lives at **https://bookaestheva.com**. Already done:

- The production D1 database `aestheva` exists in the Haswel Care Cloudflare account, in the Asia-Pacific region, with the schema applied and recorded as migration `0001_init.sql`. Its id is in `wrangler.jsonc`. It holds no venues; real providers join through onboarding. Never load `seed/dev-sample.sql` into it.
- `bookaestheva.com` was registered through Cloudflare Registrar, so its zone is already in the same account.
- `wrangler.jsonc` attaches `bookaestheva.com` and `www.bookaestheva.com` as custom domains on deploy, and the app redirects www to the bare domain.

Remaining steps, all in the Cloudflare dashboard:

1. **Connect GitHub and deploy.** Go to **Workers & Pages**, select **Create application**, then **GitHub**. Approve access to the OMFYSDEMO account if asked, choose the **Aestheva** repository, keep the project name `aestheva`, choose the branch `claude/data-build-dashboard-5qxapk`, leave the build and deploy commands as they are, and select **Deploy**. Every later push to that branch deploys automatically.

2. **Razorpay keys.** In the Razorpay Dashboard, switch to **Test mode** and generate API keys. In Cloudflare, open the `aestheva` Worker, go to **Settings**, then **Variables and Secrets**, and add each of these as type **Secret**: `RAZORPAY_KEY_ID` (starts `rzp_test_`), `RAZORPAY_KEY_SECRET`, and `PREVIEW_KEY` (any long random phrase you choose; it unlocks hidden venues). Use Secret even for the key id: plain-text variables added in the dashboard are reset by the next deploy.

3. **Razorpay webhook.** In the Razorpay Dashboard (still in Test mode), go to **Webhooks**, add `https://bookaestheva.com/hooks/razorpay`, choose a secret, and tick `payment.captured`, `payment.authorized`, `order.paid`, `refund.processed` and `refund.failed`. Add the same secret in Cloudflare as the Secret `RAZORPAY_WEBHOOK_SECRET`.

4. **Support email.** In Cloudflare, open the `bookaestheva.com` domain, turn on **Email Routing**, and forward an address such as support@bookaestheva.com to a company inbox. Then put the address in `src/config.ts`.

Check the deployment at https://bookaestheva.com/api/health. Production refuses bookings that need a deposit until the Razorpay keys are set.

If the first deploy reports a problem attaching the domain, add it by hand: open the `aestheva` Worker, go to **Settings**, then **Domains & Routes**, and add the custom domains `bookaestheva.com` and `www.bookaestheva.com`.

The top level of `wrangler.jsonc` is production. Local development runs with `npm run dev`, which uses the `dev` environment and a local database. Future schema changes go in a new file under `migrations/` and are applied with `npm run db:migrate:remote`.

### Testing payments on the live site

`providers/aestheva-test.json` is a hidden test venue, already loaded into production as a draft. It never appears in listings. Open it at:

```
https://bookaestheva.com/p/aestheva-test-clinic?preview=<your PREVIEW_KEY>
```

With Razorpay test keys, the booking page says payments are in test mode. Pay with the UPI ID `success@razorpay` or a Razorpay test card; no money moves. Try a booking with the ₹100 deposit, then cancel it from the confirmation page to see the refund. https://bookaestheva.com/api/health shows `"payments":{"mode":"test","webhook":true}` once the keys and webhook secret are in place.

The same `?preview=` link works for any draft venue, so a new venue can be checked before it goes live.

Switching to real payments later: complete Razorpay's account activation, generate Live mode keys and a Live mode webhook, and replace the three Razorpay secrets. The health check then shows `"mode":"live"` and the test-mode notice disappears.

### Adding a venue

Until the operations console exists, each venue is a file in `providers/`, such as `providers/hasta-wellness.json`. Fill in every `TODO`, then:

```sh
node scripts/provider-sql.mjs providers/hasta-wellness.json --check     # lists anything still missing
node scripts/provider-sql.mjs providers/hasta-wellness.json > venue.sql
npx wrangler d1 execute aestheva --remote --file=venue.sql
```

Photos go in `"photos"`, for example `[{"src": "/venues/hasta-wellness/reception", "alt": "Reception at Hasta Wellness"}]`, with `-400.webp`, `-800.webp`, `-1500.webp` and a 1200×630 `-og.jpg` (used when the page is shared) in `public/venues/<venue>/`. Strip location data from photos, and never publish a photo showing a client without their written consent. Shared equipment goes in `"resources"`, for example `[{"id": "hasta-laser", "name": "Laser machine"}]`, and each service that needs it lists `"resources": ["hasta-laser"]`. Two bookings can then never use the same machine at the same time, whichever practitioner takes them. Prices and deposits in the file are in rupees. Set `"status": "live"` to list the venue, `"draft"` to keep it hidden. Re-running the same file updates the venue safely: services and staff removed from the file are deactivated, never deleted, because bookings refer to them. Add verification entries only for checks that have actually been completed; the profile says "Verification in progress" until then.

### Before going live

- Fill in `src/config.ts`: support email, support phone and registered address. Pages show "to be added" markers until then. Razorpay's website review expects contact details and the cancellation, terms and privacy pages, which already exist.
- Have a lawyer review the terms and privacy pages; they are marked as drafts.
- Confirm with Razorpay that Route is enabled for this marketplace.
- Add a Cloudflare rate-limiting rule on `POST /api/bookings`. Each unpaid booking holds a slot for 15 minutes, so unlimited requests could tie up a venue's calendar.

## The marketplace dashboard

Open `dashboard/index.html` in a browser. It needs an internet connection only to load Chart.js and the fonts.

It shows gross booking value, commission earned, bookings, the cancellation and no-show rate, and confirmed value for the next 14 days. Below that are trend and category charts, a weekday-by-hour demand map, the trust and operations queue, provider performance and expansion demand. Filters cover period, source (marketplace or direct), area and category.

The bookings are **sample data**. `scripts/generate-sample-bookings.mjs` simulates them from the prototype's real catalogue: its providers, services, prices, staff hours and the 10% marketplace commission. The output is deterministic.

```sh
npm run dashboard          # regenerate sample data, then rebuild dashboard/index.html
npm run build:dashboard    # rebuild from dashboard/sample-data.json only
node scripts/build-dashboard.mjs path/to/real-data.json
```

To use real bookings, export a JSON file with the same shape as `dashboard/sample-data.json`:

- `meta`: `asOf` (YYYY-MM-DD), `launch`, `snapshot`, `ahead` (days), `commission` (0.10), `city`, `phase`
- `providers`, `services`, `staff`, `categories`, `areas`: the catalogue, referenced by array index
- `bookings.rows`: one array per booking, `[day, slot30, provider, service, staff, marketplace, status, returning]`. `day` counts days from `meta.launch`. `slot30` is the start time in 30-minute steps from midnight. `status` is 0 completed, 1 confirmed, 2 cancelled, 3 no-show. `marketplace` and `returning` are 0 or 1.
- `queue`: open provider applications and support tickets
- `cities`: expansion waitlist and readiness checks

## Decisions so far

- **Payment gateway: Razorpay.** Chosen for UPI, cards and split settlements to providers in India. Stripe was compared in October 2026 and set aside for three reasons:
  - New Indian businesses can only join Stripe by invitation.
  - Stripe Connect, its marketplace product, needs Stripe's approval before an Indian platform can onboard connected accounts.
  - Stripe's strength is international cards, while Aestheva's clients pay in rupees, mostly by UPI.
  Before integrating, confirm two things with Razorpay: that Route is enabled for a marketplace of clinics, salons and wellness centres, and the current Route transfer fee.
- **Tech stack and hosting:** Cloudflare Workers with D1, using Hono and TypeScript.

## How Razorpay fits the prototype's payment rules

The prototype's payments are simulated. These are the rules it already follows, and the Razorpay feature that would carry each one.

| Prototype rule | Razorpay |
|----------------|----------|
| The client pays a deposit online when booking. The balance is paid at the venue. | Create an Order for the deposit, take payment with Checkout (UPI and card), and confirm it from the `payment.captured` webhook. |
| Each provider is paid its share of deposits. | Onboard every provider as a Route linked account, with their own KYC and bank details. |
| Aestheva keeps 10% of the full price on completed marketplace bookings. Direct bookings carry no commission. | Transfer each deposit to the provider minus the commission, and keep the transfer on hold until the appointment is marked completed. |
| Settlements are paid weekly, on Mondays. | Release held transfers on the settlement run. Linked-account settlements then follow Razorpay's schedule. |
| Free cancellation 24 hours or more before. A provider cancellation refunds in full. Late cancellations go to an operations review. | Refund the payment. If the transfer was already released, reverse it before refunding. |
| An approved refund is taken from the provider's next settlement only when the provider is at fault. | Reverse the provider's transfer when they are at fault. Otherwise Aestheva bears the refund. |

**Open question: commission on bookings without a deposit.** Three sample services take no deposit: threading at ₹250, a haircut at ₹600 and a beard sculpt at ₹400. Commission cannot be deducted from a payment that never passes through Razorpay. The options are a minimum deposit on every marketplace booking, or invoicing those providers for commission each week.
